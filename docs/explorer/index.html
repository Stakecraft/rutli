Rütli Cluster Explorer

Rütli keeps a Canton node's namespace and signing keys as shares spread across a cluster of cosigners. Any 2 of 3 can sign together, and no single machine ever holds the whole key. Take cosigners down, breach them or destroy their disks below, then press Sign to see what still works.

Named after the Rütli meadow, where three cantons swore to act only together.

What happens when the node signs

Press Sign above. The steps light up as the request moves through the cluster in its current state.

  1. Canton asks the driver to signThe participant hands rutli-driver.jar a 34-byte digest through Canton's KMS Driver SPI. The node itself is unmodified.
  2. The driver sends a signed request to one cosignerThat cosigner leads this signing session. If it can't be reached, the driver fails over to the next one in the roster.
  3. Every cosigner checks the requestEach one verifies the driver's signed intent and applies its own policy and rate limits, so one bad cosigner can't use the others as a signing oracle.
  4. Round 1: nonce commitmentsThe leader collects commitments from enough cosigners to reach the threshold. Each nonce is marked used on disk before any share goes out, so a crash can't reuse it.
  5. Round 2: signature sharesEach of those cosigners returns a signature share. No share reveals the key.
  6. The leader combines the sharesThe result is one ordinary Ed25519 signature (RFC 8032). The whole key never existed anywhere.
  7. Canton gets its signatureCanton can't tell it from a single-key signature. The driver's hash-chained audit log records it, and so does the journal of each cosigner that took part.
Result

Not signed yet. Press Sign to run one request through the cluster.

  • About 100 ms per 2-of-3 signature across three regions on DevNet.
  • Namespace operations are rare: the namespace key signs topology changes, while protocol signing uses the signing key, held the same way.
  • Approval quorums can also require M-of-N people to approve a signature on a protected key. This page leaves them out.

Moving an existing validator in

Same node, same namespace, same party IDs

Canton has no supported switch from database keys to a KMS. This is the in-place path we rehearsed on a Splice 0.9.0 / Canton 3.6.1 validator on DevNet.

  1. Export

    Each key is exported from the running node with keys.secret.download_to, protected by a password.

  2. Split offline

    The namespace and signing keys are split into FROST shares on an offline machine, checked against their Canton fingerprints, then refreshed so the dealt shares are useless (required in production, skipped in the DevNet drill). The encryption key is imported whole.

  3. Switch

    The same participant restarts on the Rütli driver, registers each key by id and comes back with identical fingerprints. On DevNet the wallet was down about 20 minutes, and nobody had to re-onboard.

  4. Clean up

    Not rehearsed yet

    Rotate onto keys born in the cluster, delete the old database rows and destroy every old copy. A key that once existed whole stays as exposed as its old copies.

Read with care

What this page leaves out

  • Breached here means the attacker controls the host and its seal secret. A stolen disk alone gives only a sealed share.
  • The encryption key isn't threshold-shared yet. It is sealed and replicated on every cosigner. Threshold encryption is planned for 2.0.
  • A breached cosigner can refuse to sign. The driver fails over around it, as it does for an offline one.
  • Evidence so far is DevNet. Rütli is at v0.4.0-rc.6 and not yet externally audited; the independent audit is the next step.
