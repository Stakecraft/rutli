# Rütli quickstart

Three paths, fastest first. Each is copy-pasteable and ends in something you can see working.

| Path | Time | You get |
|---|---|---|
| A. Prove the crypto | ~2 min | The FROST threshold-signing tests pass on your machine |
| B. Canton node on Rütli | ~5 min | A real Canton participant whose keys are generated + signed through the driver |
| C. Namespace key in MPC | ~15 min | The same node, but its Ed25519 namespace key lives in a 3-node FROST cluster |

## Prerequisites

- **JDK 17** (`java -version` → 17). Canton runs on 17; the driver jar is compiled for it.
- **sbt** (`brew install sbt`) — paths B, C.
- **Rust** (`rustup`) — path A, or building the cluster from source in C.
- **Docker** — path C (running the cluster).
- **Canton 3.5.6** community release for paths B, C:
  ```sh
  # download + extract, then:
  export CANTON_HOME=/path/to/canton-open-source-3.5.6
  ```
  https://github.com/digital-asset/canton/releases/tag/v3.5.6

---

## Path A — prove the threshold crypto (~2 min)

No Canton, no JVM. Runs the FROST core + cosigner tests: DKG, threshold signing, nonce-reuse
refusal, refresh, share repair, sealed-share recovery — all verified against a strict Ed25519
verifier.

```sh
cd frost
cargo test
```

Green means: a 2-of-3 cluster can generate a key nobody holds whole, sign Canton's payload, and the
signature verifies — the whole premise, on your laptop.

---

## Path B — a Canton node running on Rütli (~5 min)

A participant boots with `crypto.provider = kms` → the Rütli driver generates all its keys
(including an **Ed25519 namespace key**) and signs its identity topology through them. Backend here
is the in-process software one (testing only — no cluster needed).

```sh
# 1. Resolve the Canton KMS driver API (not on Maven Central) into your local ivy repo — once.
scripts/publish-canton-deps.sh v3.5.6

# 2. Build the driver jar.
sbt driver/assembly            # -> driver/target/scala-2.13/rutli-driver.jar

# 3. Boot a devnet participant on the driver and run the smoke test.
CANTON_HOME=/path/to/canton-open-source-3.5.6 deploy/devnet/up.sh
```

You'll see the participant reach `initialized` and print its identity + the keys the driver made:

```
=== rutli Phase 0 smoke test ===
participant id (namespace = fingerprint of driver-held key):
PAR::participant1::1220...
  ... keySpec = EC-Curve25519, usage = namespace ...
=== OK: identity initialized and topology signed via rutli ===
```

Reaching `initialized` *is* the proof — the node cannot init without the driver generating the
namespace key and signing its identity topology with it.

## Path C — the namespace key in a FROST MPC cluster (~15 min)

Now the namespace key is generated by distributed key generation across a 3-node cluster and every
signature is a 2-of-3 threshold signature. No machine — including the Canton node — ever holds the
whole key.

```sh
# 1. Start a 3-node cosigner cluster (dev: plaintext, on localhost:9101-9103).
docker compose -f deploy/frost/docker-compose.yml up --build -d

# 2. Build the driver jar (skip if you did Path B).
scripts/publish-canton-deps.sh v3.5.6 && sbt driver/assembly

# 3. Boot the participant pointed at the cluster (backend = frost). DKG runs on first init.
CANTON_HOME=/path/to/canton-open-source-3.5.6 \
  CANTON_CONF=canton-frost.conf \
  deploy/devnet/up.sh
```

Same `=== OK … ===`, but now the namespace key was **born distributed**. Confirm the shares landed
on the three cosigners:

```sh
for c in 1 2 3; do echo "cosigner$c:"; docker compose -f deploy/frost/docker-compose.yml \
  exec -T cosigner$c ls /data/keys; done
# each shows frost-participant1-namespace.json — one share per node
docker compose -f deploy/frost/docker-compose.yml down    # tear down
```

For **mutual TLS + sealed shares**, use `docker-compose.tls.yml` (see
[`deploy/frost/README.md`](deploy/frost/README.md)); for **Kubernetes**, see
[`deploy/k8s`](deploy/k8s).

## Where to go next

- **Production**: [`deploy/k8s`](deploy/k8s) or `deploy/frost/docker-compose.tls.yml` (mTLS + sealed
  shares), then run the **key ceremony** ([`docs/key-ceremony.md`](docs/key-ceremony.md)) to birth a
  real namespace key with witnesses and a signed record.
- **Controls**: turn on the hash-chained audit log, M-of-N signing approval
  ([`docs/approval-quorum.md`](docs/approval-quorum.md)), the signing journal, and a proactive-refresh
  schedule.
- **Operations**: [`docs/disaster-recovery.md`](docs/disaster-recovery.md) — backup/restore and the
  loss/recovery matrix. **Do this before go-live** — the namespace key is non-rotatable.
- **How it works**: [`docs/architecture.md`](docs/architecture.md) and
  [`docs/phase-2-frost.md`](docs/phase-2-frost.md).

## Troubleshooting

- **`sbt driver/assembly` OOMs or hangs** — give it heap: `SBT_OPTS="-Xmx4g" sbt driver/assembly`,
  and make sure only one sbt runs at a time (concurrent sbt fight over the ivy lock).
- **`UnsupportedClassVersionError` when Canton loads the jar** — the jar must be built with JDK 17 as
  the target (the build pins `-release 17`); check your `java -version`.
- **`publish-canton-deps.sh` — `--full` needs `dpm`** — the plain form (API only) is enough for
  everything here. `--full` (for the upstream conformance suite) also needs the `dpm` toolchain.
- **Canton config rejects a key** — the node config schema tracks Canton 3.5.x; diff against the
  `reference.conf` in your `$CANTON_HOME`.
